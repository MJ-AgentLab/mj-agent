## §2 Method / 拓扑

- **Consumer**：`make_graph()`（无 checkpointer；LangGraph `create_agent` + `ALL_TOOLS` 14 工具 + `handle_sql_tool_errors` middleware）→ `agent.invoke(...)` 单轮 metric 问题。
- **Provider**：DGX vLLM `0.17.1 nvinternal` serving `nemotron-3-super`（128K ctx；reasoning 模型——thinking 走独立 `reasoning` 字段、`completion_tokens` 含 reasoning 消耗）。
- **网络（如实记录，与计划预填的偏差）**：serving 绑 DGX loopback（`127.0.0.1:8000`）→ 消费经 SSH 隧道 `ssh -N -L 18000:127.0.0.1:8000 <owner>@<DGX_HOST>`，`.env` `LLM_BASE_URL=http://127.0.0.1:18000/v1`——**非**计划预填的 LAN 直连 `http://<DGX_HOST>:8000/v1`。仍为 mj-agent 真实 runtime 到真实 DGX endpoint 的路径（响应 `model=="nemotron-3-super"` 佐证）。
- **`.env` 切换面**（T-4 演练 2026-07-03 已持久化，ADR-030 secrets.enc 管道）：`LLM_PROVIDER=local-openai-compat` + `LLM_MODEL_ID=nemotron-3-super`（≠ 默认 Ark 云 id）+ `NO_PROXY`（本机 Clash 代理适配）；api-key 无需（401 判别 = 200 无鉴权，`"EMPTY"` sentinel 生效）。
- **捕获机制**：脚本级 `httpx.Client.send` tee（零 src 改动）；非流式完整响应体 raw JSON；redact 后 LAN IP → `<DGX_HOST>` 占位（复核 0 残留）。

**触发问题（verbatim）**：`查询量 qrynum 这个指标属于哪个业务域？只用 find_biz_context 做目录召回并回答，不要查询数据库。`（metric 类 → system prompt 硬规则强制 `find_biz_context`，纯本地 YAML 零 DB；一轮同产两类响应。）

## §4 Observations

1. **隧道拓扑是当前消费路径的运行时事实**：serving loopback-bound（dgx-mlops 侧部署姿态）；隧道 password 认证不可无人值守——耐久解（serving LAN 绑定 + `--api-key`）已作 D-question 移交 dgx-mlops（readiness 回报 2026-07-03 §1.3）。
2. **reasoning 模型 token 经济**：mj-agent 常规 trajectory 起步 ~19.6K input tokens（system prompt + 8 runtime skills）；`completion_tokens` 含 reasoning 消耗——评测/预算口径须注明。
3. **provider 稳定性事件（同日，另见 readiness 回报 §2.3b）**：smoke 长链（22.5K ctx）曾触发 vLLM `EngineCore` CUDA fatal（`cudaErrorUnknown`）→ 容器自动重启后复测双 PASS = 偶发非确定性；已移交 dgx-mlops M4 runbook 排障。本 e2e 捕获轮全程无异常。
